# Feature: Roles, trainers and guest mode

Objective: admin, trainer and user roles; trainers coach many students (and students have many trainers) through a profile invite link; guests try the app without an account, keeping their data in the browser. Branch: `feat/roles-and-guest` (based on `feat/workout-sessions`). Delivery: work-unit commits, `ask-on-risk` (forecast well over 400 lines: chain strategy to be asked before slicing). Test runner: Vitest (`pnpm test`, `pnpm test:integration` against `gymple_test`).

## Specs

- **S1** — User's words: "3 roles: entrenador, administrador y usaurio."
- **S2** — User's words: "El administrador puede dar de alta o certificar entrenadores, dar de baja a los mismos, editar valores como nombres, emails, dni, etc."
- **S3** — User's words: "Los entrenadores pueden tener entrenados y un link para su perfil para que se sumen sus alumnos, ver los entrenamientos de los alumnos y sugerir cargas, agregar reseñas o comentarios."
- **S4** — User's words: "Los usuarios pueden tener muchos entrenadores y los entrenadores muchos alumnos obviamente."
- **S5** — User's words: "También se podrá entrar a la aplicación como Invitado sin loguearse para que no sea obligatorio tener una cuenta para probar la aplicación" and "Lo que quiero que pase cuando carga algo un anónimo se guarde en el navegador, no quiero persistir datos de gente que no tiene cuenta".
  - Guest data never reaches the server; it lives in browser storage and runs the same domain rules and use cases through browser adapters of the repository ports.
- **S6** — User's words: "Registro por invitacion o que requiera validacion por email para evitar tantas cuentas spam"
  - Decision: open sign-up (name, email, password) with mandatory email verification for everyone, invited or not — the trainer link is public, so an invitation alone does not stop spam. An unverified account cannot sign in; trying to sign in re-sends the verification email. New accounts get the `user` role. Accounts created by `pnpm db:seed` are marked verified.
  - Assumption: emails go through an `EmailSender` port; production uses SMTP (nodemailer, configured by `SMTP_URL` and `EMAIL_FROM`), development uses a Mailpit container in `docker-compose.yml`, tests use an in-memory fake. Verification links use better-auth's default expiry.
- **S7** — User's words: "un entrenador puede ser a su vez un asesorado de otro entrenador, es algo bastante comun. Si un administrador da de baja un entrenador solamente deja de poder ejercer sus funciones de entrenador"
  - Roles are not exclusive: every account is a user (own exercises, routines, workouts, trainers); trainer and admin are capabilities added on top. A trainer can be another trainer's student (never their own).
  - Revoking a trainer only removes the trainer capability; the account, its own training data and its own trainers stay untouched.
  - Assumption: on revocation the trainer's links to their students are kept but suspended — the trainer loses access to the students' workouts and cannot add suggestions or comments, students see the trainer as inactive, existing suggestions and comments stay readable by the student. Certifying the same person again restores those links.
- **S8** — User's words: "Está bien que lo tengan solo entrenadores, que son personas certificadas por nosotros"
  - Only trainers have a DNI; it is required to create or certify a trainer and is never asked of other users.
  - Assumption: a DNI is 7 or 8 digits (dots and spaces accepted and stripped on input), unique among trainers.
- **S9** — T1b behaviour (assumptions derived from S2, S7, S8):
  - Admin capability: a flag on the account; there is no UI to grant it. The first admin is granted with a CLI script (`pnpm admin:grant <email>`). Admin pages live under `/admin`; every admin page and action checks the admin flag on the server (`requireAdmin()`); a non-admin gets a not-found page.
  - "Dar de alta": the admin enters name, email and DNI; a new account is created (verified, since the admin vouches for it) with the trainer capability, and a "set your password" email is sent (better-auth password reset flow). If the email already has an account, the admin is pointed to certifying it instead.
  - "Certificar": the admin finds an existing account by email and enters the DNI; it gains the trainer capability.
  - "Dar de baja": revokes the trainer capability (S7); "Restore" re-certifies with the stored DNI.
  - "Editar": the admin edits a trainer's name, email and DNI. Changing the email marks it unverified and sends a verification email to the new address.
  - The admin list shows trainers (active and revoked) with name, email, DNI and status, newest first.
- **S10** — User's words: "El entrenador sugiere cargas segun lo que le parezca: lo que haya hablado con su asesorado o lo que lo conozca" and "Lo ideal sería que cuando el cliente inicie un nuevo entrenamiento se actualice con esos valores sugeridos. Si el usuario no puede con esos pesos por lo que sea puede modificarlos para esa sesión"
  - A suggestion is free input from an active trainer to one of their students for one of the student's exercises: weight (kg) and reps, optional sets and note. It never changes the routine.
  - When the student logs that exercise in a new workout, the set prefill uses the suggestion instead of "last time"; the card shows it ("Suggested by Ana: 85 kg × 6"). Inside that workout, once the student logs a set, their own last set prefills the next one as today, so any change stays in that session.
  - Assumptions: a suggestion stays in effect until the trainer replaces or withdraws it; with several trainers, the most recent suggestion for that exercise wins; a revoked trainer's suggestions stop applying (S7).
- **S11** — T2 behaviour (assumptions derived from S3, S4, S7):
  - Each active trainer has a profile link `/join/<code>` (random, unguessable code; the trainer can regenerate it, which invalidates the old one). A signed-in user opening it sees the trainer's name and confirms "Join as student"; a signed-out visitor is sent to sign in or sign up and back. A trainer cannot join themselves; joining twice is a no-op; a revoked trainer's link shows that they are not accepting students.
  - Students list their trainers (active or inactive) and can leave one; trainers list their students and can remove one. Leaving or removing deletes the link.
  - An active trainer sees a student's finished workouts (history and detail, read-only) and the student's exercise names; never active workouts, routines editing, or anything of non-students. Revoked trainers see nothing (links suspended, S7).
- **S12** — Comments/reviews ("agregar reseñas o comentarios"), T3: assumption — an active trainer comments on a student's finished workout; the student reads them on the workout detail.
- **S13** — T4 behaviour (assumptions derived from S5):
  - Entry: "Continue as guest" on `/login` and `/signup` opens `/guest`, a separate route tree that needs no session and never calls the server for data (no server actions, no database). A banner on every guest page says the data lives only in this browser and links to "Create an account".
  - Guests get exercises, routines and workouts (start, log/edit/delete sets, finish with the S8 routine-update choice, history and detail) with the same domain rules and use cases: browser adapters implement the existing repository ports, persist to `localStorage` under one versioned key, and pass the same shared contract suites as the in-memory and MySQL adapters. Trainers, admin and coaching are not available to guests.
  - Guest pages reuse the existing presentational components and forms, passing browser-side functions with the same `(state, formData)` signature instead of server actions.
  - A "Delete guest data" action clears everything after a confirmation step. Storage unavailable or full shows a clear message instead of failing silently. Importing guest data into an account is S14.

- **S14** — Importing guest data into an account. User's words: "Ofrecela, que no sea automatica, si hay datos rotos se informa que algunos datos no pudieron ser cargados y se cargan los que sean válidos.. Una vez completada la migracion se borra el localstorage". Earlier exchange: the user asked "Los tenemos en el local storage, podríamos pasarlos a la base, no?" and accepted that the server validates the shape (not the truthfulness) of what it receives.
  - Offered, never automatic: a signed-in page in a browser holding guest data shows an offer to import it; nothing reaches the server until the user presses import. Assumption: "Not now" hides the offer for the rest of the browser session.
  - The server treats the payload as untrusted: it takes the user id only from the session, enforces a size limit, validates every record with the existing domain rules, gives every record a new id and rewrites every reference, so nothing can point at another user's data.
  - Valid records are imported and broken ones are skipped; the result tells the user that some data could not be imported. Records that depend on a skipped one drop only that reference (a routine item or set of a skipped exercise); a workout left with no sets is skipped. The valid part commits in one transaction: an unexpected failure imports nothing.
  - When the import completes, the guest data is removed from the browser; after a failure it stays.
  - Assumptions: a guest exercise whose name already exists in the account maps to the account's exercise (names are unique per user); archived state and workout dates are kept; the guest's active workout is imported as active only when the account has none, otherwise it is reported as not imported. The guest banner says the data can be imported after creating an account.
